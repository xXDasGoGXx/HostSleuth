# HostSleuth v1.0.0 — Release / Rollback Checklist

Status: reviewed and ready for use after explicit owner approval to publish v1.0.0.

This checklist does not itself authorize publication or production rollout.

## Preconditions

Before creating the release branch:

- v1.0 readiness closeout is merged to `main`;
- exact final `main` source is known;
- full CI is green on that exact source;
- stable/public/live/recovery remain aligned on v0.9.0;
- v0.9.0 remains the known-good rollback release;
- no unrelated feature or dependency change is mixed into the release.

## Publication

1. Re-check `main` and record the exact accepted commit.
2. Create `release/v1.0.0` from that exact commit.
3. Allow the existing Release workflow to run without modifying the release source.
4. Require the Release workflow to pass:
   - full Go tests;
   - linux/amd64 native binary;
   - linux/arm64 native binary;
   - `SHA256SUMS`;
   - GitHub tag/release;
   - multi-platform Docker image publication.
5. Independently verify:
   - GitHub tag `v1.0.0` targets the accepted source;
   - both native binaries match `SHA256SUMS`;
   - the native binary reports `v1.0.0`;
   - `mjmalleo/hostsleuth:1.0.0` exists;
   - `mjmalleo/hostsleuth:latest` resolves to the same OCI index;
   - amd64 and arm64 manifests exist.

If any publication verification fails, do not modify production or recovery.

## Recovery staging

After public verification but before production:

1. Create a focused `OMV-Docker-Rebuild` branch changing only HostSleuth from `0.9.0` to `1.0.0`.
2. Open the recovery PR but do not merge it.
3. Keep recovery `main` pinned to `0.9.0` until live v1.0.0 acceptance completes.

## Arcane production rollout

Use the existing Arcane project-management path.

Change only:

    image: mjmalleo/hostsleuth:0.9.0

to:

    image: mjmalleo/hostsleuth:1.0.0

Do not change volumes, host networking, PID/UTS settings, command, security options, or unrelated Arcane project settings.

## Live acceptance

Require all of the following before recovery merge:

### Identity / retained state

- `/api/about` reports v1.0.0;
- snapshot schema remains 4 unless a separately reviewed migration says otherwise;
- deployment mode is Docker;
- running container image is `mjmalleo/hostsleuth:1.0.0`;
- retained event history from before the upgrade remains available;
- retained Safe Action audit history remains readable where present.

### Core product surfaces

- Overview / Diagnose / Changes / Host load;
- Expectations loads;
- DNS Detective loads;
- Proxy Path loads;
- Permissions loads with native identity correctly unavailable in Docker mode;
- STARTTLS route/UI loads and a bounded real check succeeds to the expected stage model;
- Cert Rollout route/UI loads and a bounded comparison succeeds;
- Evidence Bundle read-only boundary remains intact.

### v1 hardening

- security headers are present on the live Web/API server;
- dynamic navigation/deep links work;
- no horizontal overflow at a narrow browser viewport;
- served assets remain inside accepted budgets;
- LAN `/api/actions` remains HTTP 403;
- loopback Action capability query reports `service.restart` and `service.reload` disabled/unavailable in Docker mode.

## Recovery alignment

Only after live acceptance passes:

1. update recovery documentation with the exact live acceptance;
2. merge the staged recovery PR;
3. verify recovery `main` pins `mjmalleo/hostsleuth:1.0.0`;
4. write the v1.0.0 production/recovery alignment record.

## Rollback

Known-good rollback:

    mjmalleo/hostsleuth:0.9.0

If v1.0.0 live acceptance fails:

1. use Arcane to restore the HostSleuth image tag to `0.9.0`;
2. redeploy without changing project settings or state volumes;
3. verify `/api/about` reports v0.9.0;
4. verify snapshot/events/action-audit state remains readable;
5. do not merge the recovery v1.0.0 pin;
6. document the failed acceptance and rollback evidence before another release attempt.

Disposable v1 readiness acceptance proved the same persisted state remained readable in both directions:

    published v0.9.0 -> current candidate -> published v0.9.0

No automatic rollback mechanism should be added merely for v1.0.0.

## Final alignment

A v1.0.0 release is complete only when:

- GitHub stable release = v1.0.0;
- Docker `1.0.0` and `latest` = verified same OCI index;
- live Arcane deployment = v1.0.0;
- recovery `main` pin = v1.0.0;
- production/recovery acceptance is documented;
- post-merge `main` CI is green.

Until all of those agree, describe the release state precisely rather than calling it fully aligned.
