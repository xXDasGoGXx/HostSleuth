# HostSleuth v1.0 Readiness / Hardening

Status: readiness gates satisfied; closeout in progress. v1.0.0 publication remains a separate owner decision.

## Purpose

The owner approved a feature-free v1.0 readiness cycle after stable/public/live/recovery alignment on v0.9.0.

The goal is not to invent M19. The goal is to prove that the existing HostSleuth product is coherent, durable, accessible, secure, and release-ready enough to justify v1.0.0.

## Non-goals

This readiness milestone must not add:

- a new troubleshooting story;
- a new Safe Action family;
- automatic remediation;
- a generic command/systemd/container control surface;
- multi-host controller architecture;
- monitoring/time-series features;
- broader Docker privilege;
- new cloud upload/telemetry/sharing;
- raw/unredacted evidence export.

Any such work requires a separate owner decision after v1.0 readiness.

## Gate 1 — persisted-state durability

HostSleuth must prove that persisted state from an older schema can be read and carried forward without erasing retained evidence.

The compatibility regression covers:

- a schema-1 snapshot;
- retained schema-1 event history;
- retained schema-1 Safe Action audit history;
- a current schema-4 snapshot write;
- a current event append;
- a current Safe Action audit append.

Acceptance requires the older snapshot identity/evidence to load correctly, the current snapshot to persist, and both old/new event and action-audit history to remain available.

This gate intentionally tests storage compatibility rather than changing the schema or migration model.

## Gate 2 — navigation/accessibility contract

The assembled Admin Console must provide:

- primary navigation as a tablist;
- each view selector as a tab;
- each view body as a tabpanel;
- deterministic aria-selected and tabindex state;
- aria-hidden/hidden state for inactive panels;
- ArrowLeft / ArrowRight navigation;
- Home / End navigation;
- visible :focus-visible treatment;
- polite live snapshot-state updates;
- reduced-motion handling;
- dynamic story tabs receiving the same semantics as static tabs.

The implementation must work for views added by the existing story asset modules, not only the four base views.

## Gate 3 — responsive / asset budget

v1.0 establishes explicit served-asset ceilings:

- HTML: <= 64 KiB;
- assembled CSS: <= 128 KiB;
- assembled JavaScript: <= 256 KiB.

These are guardrails against accidental UI bloat, not optimization targets.

Responsive regression coverage must retain the existing mobile breakpoint and the assembled console must pass a real headless-browser narrow-viewport check without horizontal document overflow.

## Gate 4 — existing security boundaries

Readiness work must not alter the accepted v0.9.0 security model.

CI and later release acceptance must continue proving:

- Docker mode exposes no native systemd action;
- service.restart and service.reload remain disabled/unavailable by default in Docker;
- Action Web/API remains loopback-only;
- Safe Actions remain independently allowlisted in native mode;
- Evidence Bundle exclusions/redaction contract remain unchanged;
- M15-M18 read-only/security boundaries remain unchanged.

## Gate 5 — release acceptance before v1.0.0

Before a v1.0.0 publication decision, HostSleuth must have:

- full Go tests;
- core race tests;
- go vet;
- native build;
- all Web JavaScript syntax checks;
- Docker smoke;
- linux/amd64 image build;
- linux/arm64 image build;
- real native restart/reload fixture;
- state-durability regression;
- accessibility/asset-budget regression;
- disposable browser/UI acceptance;
- clean-install / upgrade-state acceptance documented;
- stable/public/live/recovery release procedure reviewed against v0.9.0.

v1.0.0 publication and live/recovery rollout remain separate explicit gates after readiness source acceptance.

- architecture-specific native binary checksum is verified before installation;
