## Release procedure review

The existing Release workflow remains the accepted publication mechanism.

It:

- triggers from `release/v*`;
- validates semantic release branch naming;
- runs the full Go test suite;
- builds linux/amd64 and linux/arm64 native binaries;
- generates `SHA256SUMS`;
- creates/verifies the GitHub tag and release against the exact branch head;
- publishes a stable multi-platform Docker image only for stable semantic versions;
- publishes both the numeric Docker tag and `latest`.

The v1 publication/production/rollback procedure is captured in:

`docs/design/V1.0-RELEASE-CHECKLIST.md`

The checklist preserves the successful v0.9.0 ordering:

1. accepted source;
2. public publication;
3. independent artifact verification;
4. recovery pin staged but not merged;
5. Arcane production rollout;
6. live acceptance;
7. recovery merge/alignment;
8. final production/recovery record.

Known-good rollback remains v0.9.0 until v1.0.0 is independently verified and live acceptance passes.
